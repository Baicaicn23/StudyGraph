# Agent 工程技术调研与规划

> 调研日期：2026-10-21 ｜ 类型：知识梳理 + 决策支持 ｜ 时效敏感：🔴 极高（3–6 个月窗口）
> 证据分级：**L1** 官方文档/论文/规范 ｜ **L2** 官方博客/权威综述 ｜ **L3** 二手汇总（标注后仅作方向参考）
> 独立校验：关键事实经独立 Agent 用官方源与 arXiv 原文复核，修正 2 处（见文末「校验与修正」）。

---

## 摘要

**一句话**：MCP 解决「工具怎么被接入」，RAG 解决「知识从哪来」，编排（规划/反思/多智能体）解决「谁决定下一步」，评测解决「怎么知道没变差」——**四层各管一件事，混在一起谈就会做出又贵又不可控的系统**；绝大多数团队应该停在「单 Agent + 混合检索 + 工具治理 + 固定考卷」，只在被真实故障证伪时才加复杂度。

---

## 1. 概念对齐：先把四层分开

| 层 | 它回答的问题 | 代表技术 | 什么时候才需要 |
| --- | --- | --- | --- |
| **协议层** | 工具/上下文怎么被**发现、授权、接入** | MCP（工具互联）；A2A（Agent 互联，社区形态） | 同一能力要被**多个宿主**复用，或要接第三方系统 |
| **能力层** | 模型看不见的东西怎么给它 | 工具调用、RAG、记忆 | 需要**外部事实**或**实际动作** |
| **编排层** | **谁决定下一步** | workflow 五式、ReAct、Plan-Execute、反思、多智能体 | 任务路径**不可预知**时才交给模型 |
| **质量层** | 怎么知道**没变差** | 固定考卷、pass^k、轨迹评测、trace | 任何要上线的系统，**无例外** |

**一条判据**：Anthropic 划的线是「**控制流归代码还是归模型**」——归代码是 workflow（可控、便宜、好调），归模型才是 agent（贵、不可预测、需要护栏）。

## 2. 逐项：核心概念 / 典型场景 / 实现方式 / 落地要点

### 2.1 MCP（Model Context Protocol）

**核心概念**
开放标准，JSON-RPC 2.0 之上，三个角色：host（宿主应用）/ client（宿主内每个 server 一个）/ server（提供能力的一端）。
服务端三原语：**tools**（模型决定调用）/ **resources**（应用或用户挂载的只读上下文）/ **prompts**（用户主动选用的模板）。
客户端三原语：**sampling**（server 回调宿主模型）/ **roots**（server 询问文件系统边界）/ **elicitation**（server 中途向用户追问）。

**规范现状（截至 2026-07-28 修订）**
按**日期**版本化，当前修订版 **2026-07-28**（前一版 2025-11-25）。主要变化：移除协议级 session 与 `initialize` 握手、改为**无状态**（每个请求自带版本与能力）；新增 `server/discover`、`subscriptions/listen`、多轮请求 `InputRequiredResult`、统一 `resultType`；**`roots` 与 `sampling` 已标记 deprecated**。
2025-06-18 版确立的安全口径仍在：HTTP 场景按 **OAuth 2.1 资源服务器**处理，配合 RFC 8707 资源指示器。

**与 function calling 的边界**
function calling 标准化「一次会话内的调用格式」；MCP 标准化「跨宿主的发现、授权、接入」。官方类比是 **LSP**（把 N×M 集成问题变成 N+M），不是「USB-C」（那是官网的通俗说法）。

**典型场景**
内部系统（文件、数据库、工单、检索服务）封装一次，多个 AI 宿主复用；本地工具用 stdio；远端多用户用 Streamable HTTP + OAuth。

**工程落地要点**
1. 只把**稳定、边界清晰**的能力做成 tool；纯读的上下文优先做成 resource（省一次工具调用）。
2. **错误用 `isError` 返回**，不要跨协议抛异常——异常会让调用方拿到不可解释的失败。
3. 工具**数量要克制、职责不重叠**：重叠是模型选错工具的首要原因。
4. 版本按日期协商，不要硬编码「最新版」；服务端要能回答「你支持哪些版本」。
5. `roots`/`sampling` 已 deprecated，新项目不要再依赖这两个原语做核心设计。

### 2.2 RAG（检索增强生成）

**核心概念**
把**外部可验证的上下文**注入，而不是改模型权重。定位判据：**事实归 RAG，形式归微调**——要新鲜、要可删、要能给出处，就走 RAG。

**四类架构**
| 类型 | 结构 | 适用 |
| --- | --- | --- |
| Naive | 向量检索 → 生成 | 只适合原型 |
| **Advanced（生产主流）** | query 变换 → hybrid（BM25+向量）→ RRF 融合 → **cross-encoder 精排** → 后置校验 | 80% 的场景 |
| Modular | 组件可换（检索器/生成器/评估器/路由器） | 多来源、多租户 |
| GraphRAG | 抽实体建图 → 图遍历/社区聚合 | 多文档聚合、关系型问题 |

**工程要点**
1. **切块优先于换模型**：结构感知切块（按页、按标题）比调 embedding 收益大得多；切口要保得住「出处」（页码/章节）。
2. **两级漏斗**：bi-encoder 粗排负责「快而广」，cross-encoder 精排只对 **top 50–100** 逐条打分（10–100ms/条）。
3. **混合检索是默认项**，不是优化项：纯向量在专有名词、短词、编号上会漏。
4. **先有考卷再谈优化**——没有固定题目与基线，任何「我换了模型感觉更准」都不可验证。

> 参考数据（**L3 二手汇总，未回溯原始论文**，仅作方向参考）：hybrid top-1 召回 53.4% vs dense 48.7% / sparse 22.1%；精排约 +28% NDCG@10、幻觉下降约 35%。

### 2.3 工具调用（Tool Use / Function Calling）

**核心概念**：模型输出结构化参数，宿主执行并把结果回填。是所有 Agent 模式的底座（ReAct、Plan-Execute 都建立在它之上）。

**工程要点（ACI：Agent-Computer Interface）**
官方经验：**优化工具接口比优化 prompt 更值钱**。工具要命名清晰、参数精确、给示例、写清边界、错误行为简单可预期。
治理四件套：
1. **超时**（单次）+ **有限退避**（只对可重试错误，别对参数错误重试）；
2. **失败转成工具消息**，不让单点故障炸整回合；
3. **权限分层**：模型「看得见哪些工具」与「能不能真跑」分开管；
4. **写操作前置人工确认**（HITL）——这是承诺，不是提示词。
另：能并行的调用就并行（同轮多工具之间通常无数据依赖）；但**写库类工具并发要小心锁竞争**。

**评测**：BFCL 这类基准测「调用可靠性」（含并行、多轮、畸形 schema），但真正该测的是**你自己的 schema**。

### 2.4 上下文管理（Context Engineering）

**核心概念**：上下文是**有限资源**，长不等于好（长上下文会降低召回与聚焦）。
**三种手段**（官方给的三招）：
- **compaction**：把长历史压成摘要再开新窗口；
- **structured notes**：把关键事实、目标、决策**外置**到上下文之外（文件/笔记）；
- **sub-agent**：让子代理在独立窗口里干重活，只回传蒸馏结果（约 1–2k token）。
另加 **just-in-time 检索**：上下文里只放「路径/查询/链接」，需要时用工具去取。

**落地要点**：压缩必须从**整轮边界**裁，不能把「工具调用—工具结果」这对拆散（拆散会让模型看到孤立结果而报错）；摘要要有**字数上限**，否则压缩本身变成新的膨胀源。

### 2.5 记忆（Memory）

**核心概念**：认知科学四分类——working（当前推理用的上下文）/ semantic（稳定事实）/ episodic（具体经历）/ procedural（可复用流程）。

**代表工作**
- **Generative Agents**（arXiv:2304.03442）：memory stream + 定期 reflection + 按 recency/importance/relevance 三因子检索；
- **MemGPT**（arXiv:2310.08560）：把 LLM 当 OS，主上下文/外部存储分层，模型用函数调用自主换入换出；
- **MemoryBank**：引入遗忘曲线式衰减；
- **LongMemEval**（ICLR 2025）：把长期记忆拆成五能力——抽取、多会话推理、时间推理、知识更新、拒答。

**最该记住的一条结论（已校验修正）**
LongMemEval 的实际结论是「**简单的记忆设计在时间推理上表现差**」（时间推理得分最低 0.435）；而「知识更新」更多是**既有基准未覆盖**的能力，现成系统在该项反而较高（0.833）。
→ 工程含义：**先做「时间戳 + 更新/失效」这套基础管线，再谈花哨的检索策略**。记忆的难点不是「存得多」，而是「**删得对**」——过期、被推翻、互相冲突的记忆必须有处置路径。

### 2.6 规划与反思（Planning / Reflection）

| 模式 | 机制 | 适合 | 代价 |
| --- | --- | --- | --- |
| **ReAct**（arXiv:2210.03629） | Thought→Action→Observation 交替 | 路径需随工具结果调整 | 思考文本费 token |
| **Plan-and-Execute** | 先出完整计划，再逐步执行 | 步骤可预知、工具慢 | 适应性差 |
| **Reflexion**（arXiv:2303.11366） | 失败后写「口头反思」存记忆，下一轮带上 | 可重复试错的任务 | 需要多轮预算 |
| **Self-Refine**（arXiv:2303.17651） | 单轮内 critique→rewrite | 有明确评价标准 | 收益不稳定 |

**关键风险（必须写进设计）**：同一个模型既写又评会**共享盲区**——它看不见的错误，复核时也看不见；甚至会出现「自信地改坏一个好答案」。缓解：**给批评一个外部锚点**（测试、schema 校验、工具结果），并把重试设**硬上限**；批评要说明「为什么失败」，否则重试等于盲重摇。

### 2.7 多智能体（Multi-Agent）

**四种拓扑**：supervisor/hierarchical（主管派活）、peer/mesh（对等协商）、pipeline（流水线）、blackboard（共享黑板）。

**适用条件（缺一不可）**
1. 子任务**可以独立推进**（不需要频繁共享中间状态）；
2. 每个子任务**各自需要大量上下文**（单窗口塞不下）；
3. 子结果可以**蒸馏成短摘要**回传（1–2k token）。

**代价**：成本与延迟上升、失败模式变多、可解释性下降、调试成本陡增。
**建议**：**默认不上**。先做「单 Agent + 按意图切换角色提示词」（同一张图、不同人格），只有当上下文互相污染成为**实测瓶颈**时才拆。

### 2.8 评测（Evaluation）

**三层，缺一层就会自欺**
| 层 | 评什么 | 判据 |
| --- | --- | --- |
| final-answer | 最终答案对不对 | 确定性校验（不是看文字像不像） |
| **trajectory** | 路径合不合理：工具选对没、有没有绕圈、有没有越权 | 步数/循环检测/工具调用正确性 |
| per-turn | 单轮是否跑偏（越狱、泄漏、政策违反、用户情绪） | 轻量分类器 |

**可靠性指标 pass^k**：k 次独立试验**全部成功**的概率。τ-bench 的实测是 GPT-4o 零售域 **pass^1 ≈ 61%、pass^8 < 25%**——**只报 pass@1 会把「偶尔能成」包装成「稳定可用」**。

**三个最常见的坑**
1. 只报 pass@1；
2. 没有**状态快照**，失败轨迹无法重放（评测就成了黑盒）；
3. 把「完成了」当「正确完成」——agent 会自信地说「已下单」，而数据库里什么也没有。

## 3. 各技术的定位与适用条件

| 技术 | 定位 | 必须上的信号 | 不该上的信号 | 主要成本 |
| --- | --- | --- | --- | --- |
| **MCP** | 工具接入的标准化 | 同一能力多宿主复用 / 要接外部系统 | 只有一个内置工具集、不对外 | 协议与授权复杂度 |
| **RAG** | 事实来源与可追溯 | 答案必须来自自有资料、需给出处 | 纯生成/创作类任务 | 切块与检索调优、评测集 |
| **工具调用治理** | 让动作可控 | Agent 会**改数据**或**调外部 API** | 只读问答 | 权限模型、审计 |
| **上下文压缩** | 长会话可用性 | 会话超过窗口 / token 成本失控 | 单轮短问答 | 摘要质量、信息损失 |
| **记忆** | 跨会话连续性 | 需要「记住用户/进度」 | 每次任务独立 | 写入策略、失效与冲突 |
| **规划** | 多步任务可完成 | 步骤数不可预知 | 固定流程（用 workflow） | token、延迟 |
| **反思** | 质量兜底 | 有外部锚点可判对错 | 无客观判据、预算紧 | 成本翻倍、可能改坏 |
| **多智能体** | 并行深领域 | 子任务独立 + 各自吃大量上下文 | 单窗口能装下 | 成本、可解释性 |
| **评测** | 一切的前提 | **任何要上线的系统** | 无（不可省） | 出题与维护 |

## 4. 组合方案：三档，按「被证伪才升级」

> 原则：**每一档都必须有对应的判据**才允许升级，不允许「因为看起来先进」而加层。

### 第一档 · 最小可用（MVP）
`单 Agent（ReAct）+ hybrid RAG + 工具治理（超时/失败转消息）+ 固定考卷 + 基线`
- 覆盖：能答、能查、能算、坏了不炸、变差能发现。
- 明确不做：MCP、记忆、反思、多智能体。
- 判据：检索召回与意图分类有基线，且改动会跑门禁。

### 第二档 · 生产可用
`+ MCP 接入外部系统 + 精排 + 上下文压缩 + 写操作 HITL + trace 轨迹`
- 升级判据（满足才升）：① 需要接 2 个以上外部系统；② 召回精度成为瓶颈（有漏召回实例）；③ 会话经常超过窗口；④ 存在「模型改数据」的风险面。
- 明确不做：多智能体、复杂记忆巩固。

### 第三档 · 高可靠
`+ pass^k 式多次试验 + 记忆生命周期（写入/失效/替换/冲突消解）+ 轨迹级评测 + 任务成功率 Benchmark`
- 升级判据：已上线、有真实流量、失败**代价高**（钱/合规/不可逆）。
- 多智能体仍属**可选**：只有当「子任务独立 + 各自吃大量上下文」同时成立才拆。

### 组合示意（谁依赖谁）
```
评测（底座，贯穿全程）
   ├── RAG ── 需要出题与基线才谈得上优化
   ├── 工具治理 ── 权限/超时/失败转消息是 Agent 能跑的前提
   ├── 编排（ReAct/Plan） ── 依赖上面的工具与检索
   ├── 上下文压缩 / 记忆 ── 依赖编排跑起来后暴露的问题
   └── MCP ── 是「接入方式」，可在任一层插入，不改变上层逻辑
```

## 5. 落到本项目（知迹）：优先级与依据

**现状对照（结论来自代码核对，非印象）**

| 关注点 | 现状 | 判定 |
| --- | --- | --- |
| Run 持久化 / 中断恢复 | 显式状态图 + SQLite 检查点 + `interrupt/resume` + 线程级联清理 | 🟢 具备 |
| 工具治理 | 双层权限 + 同轮并发 + 超时/退避/失败转消息 + 写操作 HITL + MCP 注册 | 🟡 部分（无参数级权限、大结果落盘） |
| 上下文压缩 | 抽取式摘要（240 字上限）+ token 预算 | 🟡 部分（无 LLM 摘要/关键事实外置） |
| 记忆 | 按课程隔离 + 写入前确认 + 规则抽取 | 🔴 弱（**无失效/替换/删除/冲突消解**） |
| 评测 | 检索 35 题 + 意图 15 句门禁 + 消融 + 284 离线测试 | 🟡 部分（**无任务成功率级 Benchmark**） |
| 知识层 RAG | 四路召回 + 加权 RRF + 词面精排 + 页级出处 | 🟢 具备 |

**建议的下一步（按 ROI 排序，均可在现有评测体系内验证）**
1. **难例考卷**（前提）：当前真向量下 35/35 已饱和，没有难例就测不出任何改进。加长文档、强干扰项、跨库同名。
2. **记忆生命周期**（最弱的短板）：给记忆加时间戳与状态（有效/被替代/失效），写入前做冲突检测；这一项能直接对上 LongMemEval 指出的「时间推理」短板。
3. **任务级 Benchmark**（把评测升维）：从「检索命中」升级到「一次会话是否达成目标」，用确定性状态校验而非 LLM 判分；并引入 pass^k 看待稳定性。
4. **MCP 只做「接入」**：不自研协议层；把「文件工作区」这类能力做成 server，验证跨宿主复用。

**明确不做（有依据的建议）**
- **多智能体**：单用户学习场景，子任务不需要各自吃大量上下文；拆了只会把「可解释」这个优势搭进去。
- **反思节点**：没有独立外部判据（答案对错由学科事实决定，模型自评比生成更不可靠），成本翻倍而收益不确定。

## 6. 反模式清单（决策时先对照）

| 反模式 | 症状 | 后果 |
| --- | --- | --- |
| 用 agent 做 workflow 的事 | 步骤本来就固定，却让模型决定流程 | 贵、慢、不可复现 |
| 先上多智能体再找理由 | 架构图很好看，任务成功率没变 | 调试成本翻倍 |
| 只报 pass@1 | 「演示时能成」 | 上线后随机失败 |
| 没有状态快照 | 失败无法重放 | 评测是黑盒，无法归因 |
| 把「完成」当「正确完成」 | Agent 说「已保存」，库里没有 | 数据不一致且难以发现 |
| 用同一模型自评当质量闸门 | 错误被复核通过 | 自信地交付坏结果 |
| 记忆只增不删 | 过期偏好一直被引用 | 答非所问且无法解释 |

## 校验与修正（独立 Agent 复核，2026-10-21）
