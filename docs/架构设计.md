# StudyGraph 架构设计

> 这份文档回答三个问题：**一次回合是怎么跑的**、**每个模块负责什么**、
> **为什么这么设计、不这么设计会怎样**。代码入口在 `src/studygraph/`。

## 一、设计目标

StudyGraph 是一个面向大学生的个人学习助理。它的产品诉求很具体：

1. 平时把资料**分学科**沉淀进知识库；
2. 聊天时能**检索自己的资料**来讲解、并给出处；
3. 期末能从知识库和错题**自动出题**、安排复习；
4. 写操作（把内容存进知识库）要**先经过用户确认**。

技术诉求是：用 **LangGraph** 把上面这条流程做成一张**显式、可观测、可断点续跑、
可人工介入**的状态图，而不是把逻辑藏在一个隐式的 Agent 黑盒里。

## 二、为什么是 LangGraph（而不是手写循环或普通链式封装）

不是"因为框架新"，而是因为下面四件事正好命中了这个项目的真实需求：

1. **状态是显式的。** 意图、子智能体、选中的知识库、工具轮数都写在
   `StudyState` 里（`state.py`）。出问题能一眼看到"卡在哪一步、状态是什么"。
2. **检查点是内建的。** `AsyncSqliteSaver` 让会话可以**断点续跑**——这也正是
   Human-in-the-Loop 的前提：中断之后要从断点恢复，而不是从头再跑。
3. **Human-in-the-Loop 是一等公民。** `interrupt()` / `Command(resume=...)`
   把"暂停等用户确认"做成了图的原语（见 `tools.save_note`），不需要自己设计。
4. **流式是内建的。** `stream_mode="messages"` 直接产出模型 token，
   不用自己解析 SSE。

代价要说清楚：框架会替你决定循环怎么转、状态怎么存。StudyGraph 的做法是
**只把编排交给 LangGraph，把"决策与权限"留在自己的代码里**（见第五节）。

## 三、一次学习回合的数据流

```text
用户消息
  │
  ▼
[route 节点]  规则分类 → 意图(intent) → 子智能体(agent) + 工具权限
  │
  ▼
[agent 节点]  用子智能体的角色提示词 + 允许的工具清单调用模型（astream 聚合）
  │
  ├── 模型返回工具调用 ──▶ [tools 节点] 执行层权限检查 → 执行工具（可 interrupt）──┐
  │                                                                              │
  └── 模型返回最终回答 ──▶ END                                                     │
                                                                                 │
                                    ◀───────── 回到 agent 继续推理 ───────────────┘
```

对应的图定义（`graph.py`）：

```text
START ─▶ route ─▶ agent ─┬─(有工具调用且未超轮数)─▶ tools ─▶ agent
                         └─(无工具调用)─────────▶ END
```

- `route` 是入口，负责"分诊"。
- `agent ⇄ tools` 是标准的 Agent Loop；用 `tool_rounds` 上限兜底，防止工具循环失控。
- 条件边 `should_continue` 决定是继续调工具还是结束。

## 四、状态模型

`StudyState`（`state.py`）是一个 `TypedDict`：

| 字段 | 类型 | 作用 |
| --- | --- | --- |
| `messages` | `Annotated[list[AnyMessage], add_messages]` | 对话历史；归约器负责**追加**而非覆盖 |
| `user_id` | `str` | 用户标识（多用户隔离预留位） |
| `intent` | `str` | 本回合识别出的意图 |
| `agent` | `str` | 路由到的子智能体名 |
| `knowledge_bases` | `list[str]` | 本轮选中的知识库；检索工具据此限定范围 |
| `tool_rounds` | `int` | 已执行的工具轮数，防止死循环 |

> **为什么要用 `add_messages`？** 节点返回 `{"messages": [新消息]}` 时，归约器
> 把它追加进历史，而不是替换。Agent Loop 就是靠这个把"模型消息→工具消息→
> 模型消息"一条条接起来的。

## 五、子智能体与工具最小权限（双层）

### 5.1 意图 → 子智能体

`routing.classify()` 是一个**纯规则、确定性、零成本**的分类函数，覆盖六个意图：
讲解、练习、进度、检索、计算、闲聊。顺序与关键词见 `routing.py`。

意图映射到 `AGENT_PROFILES` 里的一个角色（`tutor / practice / progress /
retriever / calculator / chat`），每个角色带自己的系统提示词和工具策略：

| 子智能体 | 默认工具 | 黑名单 | 定位 |
| --- | --- | --- | --- |
| `tutor` | 检索 + 计算器 + 沉淀 | — | 讲解，资料里有的优先检索 |
| `practice` | 检索 | **沉淀** | **只读**：能基于资料出题，不改动数据 |
| `progress` | **无**（`deny_all`） | 全部 | 只依据档案回答 |
| `retriever` | 检索 + 沉淀 | — | 资料检索并给出处 |
| `calculator` | 计算器 | 检索 | 只算，不查资料 |
| `chat` | 检索 + 计算器 + 沉淀 | — | 通用兜底 |

**权限按"读 / 写"分档，而不是按"给 / 不给"分。** `progress` 全禁、`practice`
只读、其余可读写——同一个路由表里三种档位并存，这才是最小权限该有的样子。

### 5.2 双层生效

- **schema 层**：`agent` 节点只把 `allowed_tools(profile)` 里的工具
  `bind_tools` 给模型——被禁的工具**模型根本看不见**。
- **执行层**：`tools` 节点对每个工具调用再查一次 `is_tool_allowed(profile, name)`，
  命中黑名单就返回 `[tool_not_allowed]`——即使模型被幻觉带偏、硬请求了被禁工具，
  **也执行不了**。

两层缺一不可：只做第一层，模型仍可能"说出"工具名；只做第二层，模型会反复
尝试被禁工具、浪费轮数。

### 5.3 为什么不用 LangGraph 自带的 `ToolNode`

`ToolNode` 很方便，但它默认会执行模型请求的**任何**已注册工具，没有一个自然的
位置挂"按子智能体做权限判定"。所以这里用一个自定义 `tools` 节点：既做执行层
权限拦截，又保证工具里的 `interrupt()`（HITL）能正常抛出。

## 六、知识库与中文检索

`knowledge.py` 用 SQLite + **FTS5 trigram** 做全文检索。

### 6.1 为什么是 trigram

FTS5 默认的 `unicode61` 分词器**不切中文**——整段中文会被当成一个 token，
中文查询 `MATCH` 必然零命中。`trigram` 分词器把文本按 3 字滑窗切分，中文因此
可以被索引和命中。

### 6.2 查询怎么构造

天然语言问句几乎**不可能**是资料里的连续子串，所以不能把整句当成 FTS 短语。
`build_match_query()` 把查询拆成词项后做 **OR**：

- 中文按 **3-gram 滑窗**拆（`"特征值描述什么"` → `"特征值" OR "征值描" OR …`）；
- 英文/数字整词保留；
- 用 OR 拼接成 FTS5 查询串，`bm25` 按命中程度排序。

### 6.3 短词兜底

trigram 要求命中词 ≥3 字符，两字词（如"导数"里的两字查询）进不了 FTS 通道。
这时 `_search_like()` 用 `LIKE` 兜底。

### 6.4 出处与范围

每条命中都带 `library`（哪个学科库）与 `title`（哪份资料），回答据此给出处；
`search()` 支持按选中的知识库限定范围（`knowledge_bases` 经 contextvar 传入工具，
不污染模型可见的参数 schema）。

### 6.5 向量检索与 RRF 融合（M2）

每个片段再存一个 **Embedding**（`embeddings.py`）。查询时算**余弦相似度**取
top-k，得到"语义"这一路排名；再与 FTS 的"关键词"排名用 **RRF
（Reciprocal Rank Fusion）** 融合：

```text
score(chunk) = Σ_route  1 / (k + rank_route(chunk))        # k = 60
```

RRF 只用**名次**、不用原始分数，所以能把"关键词分数"和"余弦相似度"这两种
不可比的量放在一起排序——两路都命中的片段会同时拿到两份分数，自然排前。

- **Mock Embedding** 用字符 n-gram 哈希成固定维度向量并 L2 归一化：确定性、
  零成本，且**共享子串的文本余弦更高**，足以让整条"向量 + RRF"链路被测试和演示。
- 也可切任何 OpenAI 兼容的 `/embeddings` 接口（`STUDYGRAPH_EMBEDDING_PROVIDER=openai`）。

## 七、模型适配：Mock 与 OpenAI 兼容

`providers.build_chat_model()` 按 `STUDYGRAPH_LLM_PROVIDER` 返回：

- **`mock`（默认）**：`MockChatModel`——一个**确定性的假模型**。它不是随便回一句，
  而是按固定规则**模拟工具调用**：看到算式调计算器、看到"记住/沉淀"调保存、
  看到"资料/知识库"调检索。这样**整条链路**（路由、工具循环、流式、检查点、HITL）
  都能在**零 API 消耗**下被确定性地测试和演示。
- **`openai`**：任何 OpenAI 兼容平台，通过 `langchain-openai` 接入。

> Mock 直接走 LM 接口但没有网络；测试永远跑 Mock，所以自动测试不花钱、结果稳定。

## 八、持久化与 Human-in-the-Loop

- CLI 用 **`AsyncSqliteSaver`**（`interfaces/cli.py`），检查点与会话数据存在同一个 SQLite 文件
  （不同表）。会话按 `thread_id` 隔离，**可跨进程续跑**。
- `save_note` 工具在执行时调用 `interrupt({...})` 请求确认。图在这一点**暂停**，
  CLI 打印确认信息并等待；用户回答后用 `Command(resume=True/False)` 恢复，
  工具据此决定落库还是取消。

```text
agent ─▶ tools(save_note) ─ interrupt ─┐
                                        │ 用户确认
agent ◀─ tools(继续) ◀── Command(resume=True/False)
```

## 九、HTTP 接口与前端

后端 `interfaces/api.py` 用 FastAPI 把图暴露成 SSE 流式接口；前端 `frontend/` 是一个
Next.js 16（App Router + React 19 + Tailwind）的单页聊天界面。

**为什么用 SSE 而不是 WebSocket？** 这个场景是"客户端发一次、服务端流式回"，
单向流足够；SSE 直接跑在 HTTP 之上，不需要额外的连接协议与心跳。将来要双向
（如实时推送后台任务进度）再换 WebSocket。

**接口一览**

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/api/health` | 健康检查（带当前 provider） |
| GET | `/api/knowledge/libraries` | 列出学科知识库 |
| POST | `/api/knowledge/notes` | 写入一条笔记 |
| POST | `/api/chat/stream` | 发起一回合，SSE 流式返回 |
| POST | `/api/chat/resume` | 对 HITL 中断给出确认，继续 |
| POST | `/api/knowledge/documents` | 上传资料（文本）到知识库 |
| POST | `/api/knowledge/upload` | 上传 TXT/Markdown/PDF 文件并抽文本入库 |
| POST / GET | `/api/feedback` | 记录 / 列出错题（误区） |
| POST | `/api/practice/generate` | 从知识库或错题出题 |
| GET | `/api/practice/due` | 到期练习题 |
| POST | `/api/practice/answer` | 作答自评（间隔重复 + 掌握度） |
| GET | `/api/study/plan` | 今日复习规划 |
| GET | `/api/memories` | 长期记忆 |

**SSE 事件协议**

```text
event: token      data: {"content": "..."}
event: interrupt  data: {"action": "save_note", "library": "...", "title": "...", "preview": "..."}
event: done       data: {}
event: error      data: {"message": "..."}
```

**前端怎么消费**

`frontend/src/lib/api.ts` 用 `fetch` + `ReadableStream` 解析 SSE（`EventSource`
不能发 POST，所以不用它），把事件转成回调；`Chat.tsx` 维护消息列表：
`token` 追加到最后一条助手消息（打字机效果），`interrupt` 打开确认弹窗，
确认/取消后调 `/api/chat/resume`。回答用 `react-markdown` + `remark-math` +
`rehype-katex` 渲染（公式），代码块用 `rehype-highlight` 高亮。

**为什么前端不直连模型或图？** 图里有 API Key、有权限决策、有 HITL 中断——
这些必须留在服务端。前端只是"显示器 + 确认按钮"。

## 十、分层架构与模块地图

代码按**洋葱 / 六边形**分层，依赖只朝内（`ports & adapters`）：

```text
interfaces/  ─▶ application/  ─▶ domain/
infrastructure/ ─────────────▶  (实现 application/ports 的 Protocol)
```

| 层 | 目录 | 允许依赖 | 职责 |
| --- | --- | --- | --- |
| 领域 Domain | `domain/` | 仅标准库 | `scheduling.py` 间隔重复 · `memory.py` 记忆抽取 · `quiz.py` 出题规则 · `retrieval.py` 切块+RRF · `evaluation.py` 指标 · `guardrails.py` 护栏规则 · `models.py`/`errors.py` |
| 应用 Application | `application/` | 领域 + 端口 | `ports.py` 端口 · `graph.py`/`routing.py`/`tools.py`/`state.py`（LangGraph）· `learning_service.py` · `question_writer.py` · `evaluation.py` · `trace.py` · `guardrails.py` · `tool_runner.py` · `context.py` |
| 基础设施 Infrastructure | `infrastructure/` | 应用 / 领域 | `knowledge.py` SQLite+混合检索 · `learning_repository.py` 学习仓储 · `embeddings.py`/`extract.py`/`llm.py` |
| 接口 Interfaces | `interfaces/` | 全部 | `api.py` FastAPI+SSE · `cli.py` 命令行（**组合根**：装配各层） |

**为什么这样分层（取舍）**：领域规则（排期、掌握度、出题回退）被隔离成纯函数，
测试不需要数据库和网络；外部技术（SQLite、模型、文件解析）藏在 `infrastructure/`
的端口实现后面，换实现不改业务代码。**代价**是多了一层 Protocol 与装配代码——
对当前体量属于"够用即止"，没有上完整 DDD 的实体/聚合（领域规则不复杂，硬套会造出
空转的类）。判断标准是**依赖方向是否清晰**，而不是目录层数。

## 十一、关键设计取舍（面试向）

**Q：为什么默认用 Mock，而不是直接接真模型？**
A：三个原因。① 可测试性——Mock 是确定性的，测试断言稳定、不花额度；
② 可演示性——开箱即跑，不要求用户有 API Key；③ 它迫使我们把"模型调用"和
"业务逻辑"解耦，换模型不改任何节点。Mock 甚至模拟工具调用，所以工具循环、
权限、HITL 都能在无网络下被端到端验证。

**Q：为什么意图识别用规则，而不是让模型判？**
A：规则是确定性的、零成本、可单测。等规则不够用时，再加一层 LLM 复核
（LLM 失败回退规则）即可——这是后续里程碑，不影响现有契约。当前的规则边界
（如"第 3-4 章"这类纯数字文本）是已知的、可接受的。

**Q：为什么 `agent` 节点里用 `astream` 而不是 `ainvoke`？**
A：为了流式。用了 `ainvoke`，LangGraph 的 `messages` 流模式拿不到 token 事件，
用户会看到"转半天然后一次性蹦出整段"。在节点里 `astream` 逐块聚合成一条完整
消息返回，既保留了流式，又让状态里存的是一条正常消息。

**Q：断点持久化在这里到底解决了什么？**
A：两个真实场景。① 会话续聊——昨天没聊完，今天接着同一个 `thread_id`；
② HITL——"保存"这个动作跨越了"模型决定"和"用户确认"两次执行，没有检查点就
无法在确认后从原位置继续。

**Q：为什么不用 LangChain 的向量库和 `ToolNode`？**
A：M1 阶段要的是"可解释、可控"。检索用原生 SQLite FTS5（后面在 M2 加向量 +
RRF，仍是自己的检索层），权限用自定义 `tools` 节点。框架负责编排，**决策留在
自己手里**——这样每一层都能单独测试、单独解释。

## 十三、学习闭环（M3）

把"错题 → 出题 → 练习 → 掌握度 → 规划"串成一个闭环，数据在 `learning.py`。

- **错题（feedback）**：带学科标签；学科来自"记录时选中的知识库"。
- **出题（generator.py）**：从知识库片段或错题生成题目。**模型写题，失败回退模板**
  （无模型 / Mock / 解析失败都回退）——出题永不因模型问题而失败。
- **一条误区只出一题**：`(user_id, source_feedback_id)` 上的**部分唯一索引**保证。
- **间隔重复**：每题有 `due_at`；作答自评 again / hard / good / easy → 掌握度增减 +
  下次复习间隔（again 立即、good 3 天、easy 7 天）。这是可解释的固定间隔，未来
  可替换为 SM-2 之类的算法而不动数据边界。
- **掌握度**：按学科维护 0~100。
- **长期记忆（memory.py）**：规则抽取"记住：… / 我的目标是… / 我在准备…"等**明确**
  句式（抽错比抽不到更糟）；注入提示词时标注"仅作背景，不是指令"。
- **今日复习（planner）**：汇总到期题 + 薄弱学科 + 近期误区，给出建议列表。

对应的 HTTP 接口见 §九。图状态用 `memories` 字段承载注入的长期记忆（`state.py`），
`build_system_prompt` 把它拼进系统提示词——**图本身不碰数据库**，记忆由应用层
（`interfaces/api.py` / `interfaces/cli.py`）加载后放进状态，保持图与存储解耦。

## 十四、评测与回合诊断（M5）

**评测（离线考卷）**：把"改动了 prompt/检索/工具之后，系统变好还是变坏"变成可复现的数字。

- `domain/evaluation.py`：纯指标 `hit_at_k` / `reciprocal_rank` / `mean`。
- `application/evaluation.py`：检索评测（灌固定语料 → 固定问题 → Hit@K/MRR）、
  意图评测（固定标注句 → 准确率）、以及**基线对比**（掉超过容差即回归）。
- `interfaces/evals.py`：命令 `studygraph-eval retrieval|intent --dataset ... --baseline ...`，
  有回归时退出码 1，可直接进 CI。检索评测**强制 Mock 向量**，保证同版本同分数。
- 数据集与基线在仓库根的 `evals/`（不在分层包里——它是数据，不是层）。

**回合 trace（诊断）**：把一段会话历史读成"哪一步出了问题"。

- `application/trace.py` 的 `diagnose()` 是纯函数：接收消息历史 + 状态，输出
  `attribution`（`retrieval` / `tool` / `model` / `ok`）与 `warnings`。
- `interfaces/trace.py`：命令 `studygraph-trace --thread <id>`，从检查点取历史并打印
  诊断树。归因逻辑很直接：**检索返回空结果 → retrieval；工具失败 → tool；
  没有最终回答 → model；否则 ok**。

> 为什么归因层只有四类：更细的"编排层 / 费用层"需要每回合的**事件元数据**
> （如预算回退标记、回合超时原因），当前只从消息历史推断，属于已知边界（见下节）。

## 十五、护栏、工具可靠性与上下文工程（M6）

依据业界共识（OpenAI《A practical guide to building agents》把 **guardrails** 列为核心组件、
Anthropic《Effective context engineering》讲 **上下文压缩**），补齐三个模块：

- **护栏（Guardrails）**：`domain/guardrails.py` 是纯规则——输入查空/超长/**提示词注入**，
  输出查空回答/**系统提示词泄漏**；`application/guardrails.py` 组装拒绝话术。
  接口层在进图前 `screen_input`、拿到回答后 `screen_output`（API 以 `event: guard` 告知）。
- **工具可靠性**：`application/tool_runner.py` 给每次工具调用加**单次超时**与**有限退避重试**；
  **只对可重试错误重试**（超时、网络类），参数错误立即失败。工具最终失败会转成
  `[tool_error]` 工具消息返回给模型，**不让整回合崩掉**。
  （注意：HITL 的 `GraphInterrupt` 必须原样上抛，不能被当成工具错误吞掉。）
- **上下文压缩**：`application/context.py` 在历史过长时保留最近轮次、把更早的压成一句提示；
  **裁剪只从整轮边界（HumanMessage）开始**，避免把"工具调用/工具结果"拆散。

## 十六、已知边界与路线

**已完成（M1~M6）**

- M1：状态图回合 · 意图路由 · 工具最小权限 · HITL · 检查点 · 流式 · FastAPI/SSE · Web 界面。
- M2：向量检索 + RRF 混合排序 · 知识库上传接口。
- M3：错题 / 出题 / 间隔重复 / 掌握度 / 长期记忆 / 今日复习。
- M4：资料上传与解析（TXT / Markdown / PDF）。
- M5：评测门禁（检索 Hit@K/MRR + 意图准确率 + 基线回归）· 回合 trace 诊断。
- M6：护栏（输入/输出）· 工具可靠性（超时 + 重试）· 上下文压缩。

**当前边界**

- 单用户（`user_id` 已预留，但未做隔离校验）。
- 界面是单页聊天（无登录、无多会话管理、无复习/错题界面、无文件上传 UI）。
- 间隔重复是可解释的固定间隔，不是 SM-2/FSRS 之类的自适应算法。
- 从知识库出题是"每个未用片段一道题"，没有难度分层。
- 长期记忆是规则抽取 + 平面注入，没有向量检索记忆。
- 开放题没有自动判分；自评由学习者给。

- 复习界面与错题界面（前端，由作者统一设计）。
- 出题难度分层（记忆题 / 应用题 / 迁移题）。
