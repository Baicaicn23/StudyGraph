# 知迹 架构设计

> 这份文档回答三个问题：**一次回合是怎么跑的**、**每个模块负责什么**、
> **为什么这么设计、不这么设计会怎样**。代码入口在 `src/zhiji/`。

## 一、设计目标

知迹 是一个面向大学生的个人学习助理。它的产品诉求很具体：

1. 平时把资料**分学科**沉淀进知识库；
2. 聊天时能**检索自己的资料**来讲解、并给出处；
3. 期末能从知识库和错题**自动出题**、安排复习；
4. 写操作（把内容存进知识库）要**先经过用户确认**。

技术诉求是：用 **LangGraph** 把上面这条流程做成一张**显式、可观测、可断点续跑、
可人工介入**的状态图，而不是把逻辑藏在一个隐式的 Agent 黑盒里。

## 二、为什么是 LangGraph（而不是手写循环或普通链式封装）

不是"因为框架新"，而是因为下面四件事正好命中了这个项目的真实需求：

1. **状态是显式的。** 意图、子智能体、选中的知识库、工具轮数都写在
   `StudyState` 里（`state.py`）。出问题能一眼看到"卡在哪一步、状态是什么"。
2. **检查点是内建的。** `AsyncSqliteSaver` 让会话可以**断点续跑**——这也正是
   Human-in-the-Loop 的前提：中断之后要从断点恢复，而不是从头再跑。
3. **Human-in-the-Loop 是一等公民。** `interrupt()` / `Command(resume=...)`
   把"暂停等用户确认"做成了图的原语（见 `tools.save_note`），不需要自己设计。
4. **流式是内建的。** `stream_mode="messages"` 直接产出模型 token，
   不用自己解析 SSE。

代价要说清楚：框架会替你决定循环怎么转、状态怎么存。知迹 的做法是
**只把编排交给 LangGraph，把"决策与权限"留在自己的代码里**（见第五节）。

## 三、一次学习回合的数据流

```text
用户消息
  │
  ▼
[route 节点]  规则分类 → 意图(intent) → 子智能体(agent) + 工具权限
  │
  ▼
[agent 节点]  用子智能体的角色提示词 + 允许的工具清单调用模型（astream 聚合）
  │
  ├── 模型返回工具调用 ──▶ [tools 节点] 执行层权限检查 → 执行工具（可 interrupt）──┐
  │                                                                              │
  └── 模型返回最终回答 ──▶ END                                                     │
                                                                                 │
                                    ◀───────── 回到 agent 继续推理 ───────────────┘
```

对应的图定义（`graph.py`）：

```text
START ─▶ route ─▶ agent ─┬─(有工具调用且未超轮数)─▶ tools ─▶ agent
                         └─(无工具调用)─────────▶ END
```

- `route` 是入口，负责"分诊"。
- `agent ⇄ tools` 是标准的 Agent Loop；用 `tool_rounds` 上限兜底，防止工具循环失控。
- 条件边 `should_continue` 决定是继续调工具还是结束。

## 四、状态模型

`StudyState`（`state.py`）是一个 `TypedDict`：

| 字段 | 类型 | 作用 |
| --- | --- | --- |
| `messages` | `Annotated[list[AnyMessage], add_messages]` | 对话历史；归约器负责**追加**而非覆盖 |
| `user_id` | `str` | 用户标识（多用户隔离预留位） |
| `intent` | `str` | 本回合识别出的意图 |
| `agent` | `str` | 路由到的子智能体名 |
| `knowledge_bases` | `list[str]` | 本轮选中的知识库；检索工具据此限定范围 |
| `tool_rounds` | `int` | 已执行的工具轮数，防止死循环 |

> **为什么要用 `add_messages`？** 节点返回 `{"messages": [新消息]}` 时，归约器
> 把它追加进历史，而不是替换。Agent Loop 就是靠这个把"模型消息→工具消息→
> 模型消息"一条条接起来的。

## 五、子智能体与工具最小权限（双层）

### 5.1 意图 → 子智能体

`routing.classify()` 是一个**纯规则、确定性、零成本**的分类函数，覆盖六个意图：
讲解、练习、进度、检索、计算、闲聊。顺序与关键词见 `routing.py`。
错题 / 误区类问题（「错题」「误区」「易错」「我哪里错」）归讲解私教，先做
错误归因再引导。

意图映射到 `AGENT_PROFILES` 里的一个角色（`tutor / practice / progress /
retriever / calculator / chat`），每个角色带自己的系统提示词和工具策略：

| 子智能体 | 默认工具 | 黑名单 | MCP | 定位 |
| --- | --- | --- | --- | --- |
| `tutor` | 检索 + 计算器 + 沉淀 + 错题检索 | — | ✅ | 苏格拉底式私教，先归因再引导 |
| `practice` | 检索 + 错题检索 | **沉淀** | ❌ | **只读**：能基于资料/误区出题，不改动数据 |
| `progress` | **无**（`deny_all`） | 全部 | ❌ | 只依据档案回答 |
| `retriever` | 检索 + 错题检索 + 沉淀 | — | ✅ | 资料检索并给出处 |
| `calculator` | 计算器 | 检索 + 错题检索 | ❌ | 只算，不查资料 |
| `chat` | 检索 + 计算器 + 沉淀 + 错题检索 | — | ❌ | 通用兜底 |

**权限按"读 / 写"分档，而不是按"给 / 不给"分。** `progress` 全禁、`practice`
只读、其余可读写——同一个路由表里三种档位并存，这才是最小权限该有的样子。
MCP 外部工具是第三条维度：**默认对所有子智能体关闭**（`AgentProfile.mcp_enabled`，
默认 `False`），只有 `tutor` / `retriever` 显式授权——否则每个非 deny_all 的
agent 都能拿到外部写工具（实测曾发生 calculator 拿到 `mcp_filesystem_write`
的权限泄漏，已修）。

**教学人格（分层拼装）**：`graph.build_system_prompt` 把提示词按"稳定前缀 → 动态尾
部"拼起来（前缀逐字节一致，命中上游上下文缓存）：`_BASE_PROMPT`（知迹是谁）→
`TEACHING_CHARTER`（**所有角色共享的总纲**）→ `AgentProfile.system_prompt`（**角色
专属**）→ `NOTE_STYLE_GUIDE`（只挂给会写笔记的角色）→ plan / memories / 掌握度快照。

- **总纲 `TEACHING_CHARTER`（`application/routing.py`）**：三条红线——①个人数据优先
  （知识库/错题本里有的先检索，没有的先说明再补充）；②引导优先于告知（苏格拉底式分步
  提问，学生卡住或明确要答案才给完整解）；③贴合掌握水平（注入各学科掌握度快照，从薄弱
  到较好排序，模型据此调整讲解深度）。再加三块输出契约：**输出规格**（结论先行 + 重点
  加粗 + 分层列表/表格 + 单段 ≤3 行 + 结尾必须落到下一步动作）、**技术过程内隐**（正文
  不出现工具名/接口名/字段名/执行步骤/报错，失败要内部降级成可用结论）、**绝对禁止**
  （无结构大段纯文本、跳引导甩答案、跑题、编造学习数据）。
- **分场景骨架挂在角色上**（不放进总纲，避免串味）：`tutor` 有《知识点讲解的骨架》《错题
  分析的骨架》；`progress` 有《学习规划 / 备考方案的骨架》（`| 阶段 | 核心内容 | 目标 |`
  表格落地）。**「技术过程内隐」的执行层兜底**见第十五节（输出护栏会拦正文里的工具标识符）。

### 5.2 通用工具集（联网与文件）

- `web_search`：按可用性依次回落——**DeepSeek 原生联网搜索**（主模型是
  DeepSeek 时自动启用：服务端 `web_search_20250305` 工具自己搜索、抓网页、
  解密并基于全文整理答案，一次调用覆盖全部查询角度）→ 博查（配
  `ZHIJI_BOCHA_API_KEY`，中文质量最好的付费 API）→ Tavily（配
  `ZHIJI_TAVILY_API_KEY`）→ 零配置时**必应中国 + DuckDuckGo 双路并发召回
  合并**（实测必应对部分中文查询整页跑偏，双路互相兜底）。结果按**概念覆盖**
  过滤（查询剥指令词、按空格拆段，须盖住全部段才算全相关）+ 权威度排序 +
  同域限量。瞬时错误原地重试一次，全失败转成可读提示——**诚实地说"未能联网
  核实"**，绝不带编造来源继续答题。
- `fetch_url`：抓网页正文——优先 **trafilatura** 正文抽取（导航/广告/评论
  自动剔除），正则管线兜底；**SSRF 防护**：只允许 http/https 公网地址，
  拒绝 localhost / 内网段 / file 协议。
- `write_file` / `read_file` / `list_files`：学生专属沙箱工作区
  `data/workspace/<user_id>/`。`_safe_resolve` 拒绝绝对路径、`..`、盘符与反斜杠穿越；
  写不出沙箱 → 风险可控，**不做 HITL**（与 save_note 写知识库不同）。
  **两个必须守住的点**（都踩过，见 CHANGELOG M14.1）：①`_workspace_dir()` 要返回
  **resolve 过的绝对路径**——与 `_safe_resolve` 的绝对路径对齐，否则文件写完落盘后
  `relative_to()` 抛错、对外误报"写入失败"（生产 root 是相对路径 `data/workspace`，
  而测试 fixture 用 `tmp_path` 绝对路径，天然掩盖）；②`user_id` 是客户端可传的，
  必须经 `_safe_user_segment()` 压成**单层目录名**，否则可借 `../` 在工作区外建目录写文件。

### 5.2 双层生效

- **schema 层**：`agent` 节点只把 `allowed_tools(profile)` 里的工具
  `bind_tools` 给模型——被禁的工具**模型根本看不见**（含未授权的 MCP 工具）。
- **执行层**：`tools` 节点对每个工具调用再查一次 `is_tool_allowed(profile, name)`，
  命中黑名单、或调用未授权 MCP 工具就返回 `[tool_not_allowed]`——即使模型被
  幻觉带偏、硬请求了被禁工具，**也执行不了**。

两层缺一不可：只做第一层，模型仍可能"说出"工具名；只做第二层，模型会反复
尝试被禁工具、浪费轮数。

### 5.3 为什么不用 LangGraph 自带的 `ToolNode`

`ToolNode` 很方便，但它默认会执行模型请求的**任何**已注册工具，没有一个自然的
位置挂"按子智能体做权限判定"。所以这里用一个自定义 `tools` 节点：既做执行层
权限拦截，又保证工具里的 `interrupt()`（HITL）能正常抛出。

## 六、知识库与中文检索

`knowledge.py` 用 SQLite + **FTS5 trigram** 做全文检索。

### 6.1 为什么是 trigram

FTS5 默认的 `unicode61` 分词器**不切中文**——整段中文会被当成一个 token，
中文查询 `MATCH` 必然零命中。`trigram` 分词器把文本按 3 字滑窗切分，中文因此
可以被索引和命中。

### 6.2 查询怎么构造

jieba **词级**查询优先（`build_match_query()`）：≥3 字的词直接做 FTS 短语——
比滑窗 3-gram 噪声小（3-gram 会切出"态规""划适"这类跨词垃圾）。两字词进不了
trigram 索引，走 `_search_terms_like()` 的短词路（见 6.3）；jieba 不可用或切不出
≥3 字词时回落旧 3-gram 策略。检索/入库的向量路故障时**自动降级为纯关键词检索**
（不拦 FTS 路）。

### 6.3 短词路：两字中文词的 LIKE 召回

trigram 要求命中词 ≥3 字符，而中文里信息量最高的学科术语恰恰大量是两字——
「矩阵」「秩」「导数」「极限」「概率」「队列」全都进不了 FTS 通道。

老实现只在 FTS + 向量**两路全空**时才用「整条查询当子串」兜底，于是
「矩阵的秩怎么求」要求原文出现这七个连续的字才召回，窄到几乎不可用。现在：

- `short_cjk_terms()` 用 jieba 取出查询里的**两字中文词**，剔掉疑问/指代虚词
  （什么 / 怎么 / 我的 / 这个 …，它们只会把召回掐死），最多 4 个；
- `_search_terms_like()` 对每个词做 `LIKE`，按**命中覆盖数**排序（覆盖越多越
  相关），单命中的片段也能进融合；
- 该路以 0.8 权重参与 RRF（低于字面 FTS 命中，高于靠推断的扩写路）。

### 6.4 出处与范围

每条命中都带 `library`（哪个学科库）与 `title`（哪份资料），回答据此给出处；
`search()` 支持按选中的知识库限定范围（`knowledge_bases` 经 contextvar 传入工具，
不污染模型可见的参数 schema）。

### 6.5 查询扩写：同义词与中英对照（M13）

学生用口语或简称提问，资料里写的是教材术语或英文原名——**字面不同，关键词路
就完全召不回来**。实测两个空洞：「本征值」搜不到写着「特征值」的资料、
「queue」搜不到「队列」的资料（查询与资料零字面重叠，Mock 向量路也救不了）。

做法是 `domain/synonyms.py` 的**等价术语组**（内置约 40 组：中文异名
本征值/特征值、矢量/向量；中英对照 队列/queue、矩阵/matrix；覆盖高数 / 线代 /
概率 / 数据结构 / 物理）：

- `expand_terms(query)` 找出查询命中的组，返回同组**其它**术语（查询里已有的
  不重复扩）；英文按**词边界**匹配（否则 `sort` 会命中 `consortium`）；
- ≥3 字的扩展词进 FTS 扩写路，<3 字的（如「队列」）并入短词 LIKE 路；
- `ZHIJI_SYNONYMS_FILE` 可指向 JSON 追加自定义组，内置表仍然生效。

**刻意的保守**：只收无歧义的等价词，宁可少扩不可错扩——多扩会污染精确率，
所以扩写路在融合时按 0.5 权重降权（见 6.6）。表是纯数据、匹配是纯函数，
零模型调用、结果确定性，可被评测门禁稳定复现。

### 6.6 向量检索与 RRF 加权融合（M2 / M13 加权）

每个片段再存一个 **Embedding**（`embeddings.py`）。查询时算**余弦相似度**取
top-k，得到"语义"这一路排名；再与关键词路用 **RRF（Reciprocal Rank Fusion）**
融合。检索共**四路**——原查询 FTS、扩写 FTS、短词 LIKE、向量：

```text
score(chunk) = Σ_route  weight_route / (k + rank_route(chunk))    # k = 60
weight = [1.0（原查询 FTS）, 0.5（扩写 FTS）, 0.8（短词 LIKE）, 1.0（向量）]
```

RRF 只用**名次**、不用原始分数，所以能把"关键词分数"和"余弦相似度"这两种
不可比的量放在一起排序——多路都命中的片段会叠加多份分数，自然排前。
`weights` 是 M13 加的（默认全 1.0，向后兼容）：**靠推断补出来的召回不该与
字面命中平起平坐**，否则同义词扩写引入的噪声会挤掉真正的命中。

- **Mock Embedding** 用字符 n-gram 哈希成固定维度向量并 L2 归一化：确定性、
  零成本，且**共享子串的文本余弦更高**，足以让整条"向量 + RRF"链路被测试和演示。
  但它只有共享子串相似、没有真语义——中文检索**强烈推荐接真模型**（如硅基流动
  免费的 `bge-m3`，`ZHIJI_EMBEDDING_BASE_URL/KEY` 独立配置，因为主模型是
  DeepSeek 时它没有 /embeddings 接口）；向量服务故障自动降级纯关键词检索。
- 也可切任何 OpenAI 兼容的 `/embeddings` 接口（`ZHIJI_EMBEDDING_PROVIDER=openai`）。

### 6.7 资料入库：原样秒传 + markitdown 懒解析 + 页级切块

**双轨架构：原件阅读与文本检索走两条路。**

- **上传即秒传**：PDF / Word / PPT / Excel 等二进制资料原样落盘（`kind="file"`），
  不解析、不调模型——上传永远快且零成本；阅读器里 PDF 浏览器内嵌渲染、其余格式
  下载卡片，学生看到的始终是"原件的样子"。
- **懒解析建影子索引**：需要参与检索问答时，在阅读器点「解析入库」
  （`POST /api/knowledge/doc/{id}/parse`）→ 抽文本 → 建切块/FTS/向量索引
  （kind 升级 `file_text`）。原件保留，文本视图与检索从此可用。

**抽取引擎**（`infrastructure/extract.py` 的 `extract_pages()`）：

- PDF：pypdf 按物理页抽取；
- PPTX：markitdown 转换，按其 `<!-- Slide number: N -->` 标记拆页；
- DOCX / XLSX / XLS / HTML / CSV：markitdown 整篇抽取（依赖 `markitdown[docx,pptx,xlsx]`）；
- TXT / Markdown：直接解码。

**切块策略**：页级/标题级优先——PDF/PPT 按页切块带【第 N 页】出处（见上）；
带 Markdown 标题的资料按**标题结构**切块（`chunk_markdown()`，标题做块前缀出处、
长小节再细切），无结构纯文本回落 480 字盲切（`chunk_text()`）。

**为什么按页切块**：一页 slide / 一页 PDF 是作者写内容时的天然边界，比 480 字盲切
更贴合语义；每块前缀页码出处（如`【第 3 页】`），检索命中后引文能落到具体页。
页级信息只在切块时用（`chunk_pages()`），`documents.content` 里的文本视图不带标签。

**为什么必须魔数校验**：markitdown 对解析失败的文件会**兜底按纯文本读**——
垃圾字节 docx 会"成功"读出字节内容并进索引。所以 OOXML 家族先验 PK 魔数、
老 XLS 验 OLE2 魔数，损坏/伪装文件直接 400。`.doc` / `.ppt` 老格式不支持解析
（只能下载原件），解析端明确拒绝。

**空文本 = 扫描件信号**：解析成功但零文本，说明是扫描件/纯图 PDF，
返回可读提示（视觉模型兜底在路线图上，尚未实现）。

**检索范围的两种模式**：`✦智能检索`（默认）由模型按问题从候选库挑 1-3 个相关库
（`application/library_selector.py`，编造库名过滤、选择失败回落全库）；
或用户手动勾选指定库。检索范围经 contextvar 传入工具，不进模型可见的参数 schema。

## 七、模型适配：Mock 与 OpenAI 兼容

`providers.build_chat_model()` 按 `ZHIJI_LLM_PROVIDER` 返回：

- **`mock`（默认）**：`MockChatModel`——一个**确定性的假模型**。它不是随便回一句，
  而是按固定规则**模拟工具调用**：看到算式调计算器、看到"记住/沉淀"调保存、
  看到"资料/知识库"调检索。这样**整条链路**（路由、工具循环、流式、检查点、HITL）
  都能在**零 API 消耗**下被确定性地测试和演示。
- **`openai`**：任何 OpenAI 兼容平台，通过 `langchain-openai` 接入。

> Mock 直接走 LM 接口但没有网络；测试永远跑 Mock，所以自动测试不花钱、结果稳定。

## 八、持久化与 Human-in-the-Loop

- CLI 用 **`AsyncSqliteSaver`**（`interfaces/cli.py`），检查点与会话数据存在同一个 SQLite 文件
  （不同表）。会话按 `thread_id` 隔离，**可跨进程续跑**。
- `save_note` 工具在执行时调用 `interrupt({...})` 请求确认。图在这一点**暂停**，
  CLI 打印确认信息并等待；用户回答后用 `Command(resume=True/False)` 恢复，
  工具据此决定落库还是取消。

```text
agent ─▶ tools(save_note) ─ interrupt ─┐
                                        │ 用户确认
agent ◀─ tools(继续) ◀── Command(resume=True/False)
```

## 九、HTTP 接口与前端

**为什么用 SSE 而不是 WebSocket？** 这个场景是"客户端发一次、服务端流式回"，

（如实时推送后台任务进度）再换 WebSocket。

**SSE 事件协议**

```text
event: token      data: {"content": "..."}                     # 逐块输出
event: step       data: {"kind": "thinking|tool", "title": "...", "detail": "..."}
event: status     data: {"label": "检索知识库"}                 # 状态行
event: session    data: {"id": 3, "title": "导数与极限"}        # 会话保存 / 自动标题
event: interrupt  data: {"action": "save_note", "library": "...", "title": "...", "preview": "..."}
event: guard      data: {"reason": "..."}
event: done       data: {}
event: error      data: {"message": "..."}
```

出题走另一个 SSE 端点，协议更简单：

```text
event: progress  data: {"done": 2, "total": 3, "library": "...", "difficulty": "apply"}
event: done      data: {"questions": [...]}
event: error     data: {"message": "..."}
```

**前端怎么消费**

`frontend/src/lib/api.ts` 用 `fetch` + `ReadableStream` 解析 SSE（`EventSource`
不能发 POST，所以不用它），把事件转成回调；`Chat.tsx` 维护消息列表：
`token` 追加到最后一条助手消息（打字机效果），`step` 累积成**过程卡片**（随消息落库，
历史回放可见），`session` 更新侧栏标题，`interrupt` 打开确认弹窗，
确认/取消后调 `/api/chat/resume`。回答用 `react-markdown` + `remark-math` +
`rehype-katex` 渲染（公式），代码块用 `rehype-highlight` 高亮。

过程流的渲染规则（前端）：`step` 事件按序累积到当前助手消息上；**有工具调用时默认展开**并显示
链路摘要，工具结果由 `_summarize_tool_result` 压成一句话（命中 N 篇 · 首篇：…）；回合结束时渲染
收束条（✓ 已完成 · 用时 · 后续动作）。**HITL 中断**时前端在消息里留一条"已暂停等你确认"，
后端则把中断前后的文字与步骤**合并落库成同一条消息**（`_run_stream` 的 `last_assistant_message` +
`update_message`），这样历史回放能看到完整过程。

> 另一个坑：**新增事件类型必须同步 `parseEvent` 分支**——`step` 曾漏了分支被静默丢弃。

> 踩过的坑：手写 SSE 解析时**不要硬编码前缀偏移**。`"event: "` 是 7 个字符，
> 曾写成 `slice(6)` 导致 `done` 帧永远匹配不上、出题结果恒为空——统一用
> `slice("event: ".length).trim()` 这类命名常量。

**为什么前端不直连模型或图？** 图里有 API Key、有权限决策、有 HITL 中断——
这些必须留在服务端。前端只是"显示器 + 确认按钮"。

**为什么这样分层（取舍）**：领域规则（排期、掌握度、出题回退）被隔离成纯函数，

对当前体量属于"够用即止"，没有上完整 DDD 的实体/聚合（领域规则不复杂，硬套会造出
空转的类）。判断标准是**依赖方向是否清晰**，而不是目录层数。

## 十一、关键设计取舍（面试向）

**Q：为什么默认用 Mock，而不是直接接真模型？**
A：三个原因。① 可测试性——Mock 是确定性的，测试断言稳定、不花额度；
② 可演示性——开箱即跑，不要求用户有 API Key；③ 它迫使我们把"模型调用"和
"业务逻辑"解耦，换模型不改任何节点。Mock 甚至模拟工具调用，所以工具循环、
权限、HITL 都能在无网络下被端到端验证。

**Q：为什么意图识别用规则，而不是让模型判？**
A：规则是确定性的、零成本、可单测。等规则不够用时，再加一层 LLM 复核
（LLM 失败回退规则）即可——这是后续里程碑，不影响现有契约。当前的规则边界
（如"第 3-4 章"这类纯数字文本）是已知的、可接受的。

**Q：为什么 `agent` 节点里用 `astream` 而不是 `ainvoke`？**
A：为了流式。用了 `ainvoke`，LangGraph 的 `messages` 流模式拿不到 token 事件，
用户会看到"转半天然后一次性蹦出整段"。在节点里 `astream` 逐块聚合成一条完整
消息返回，既保留了流式，又让状态里存的是一条正常消息。

**Q：断点持久化在这里到底解决了什么？**
A：两个真实场景。① 会话续聊——昨天没聊完，今天接着同一个 `thread_id`；
② HITL——"保存"这个动作跨越了"模型决定"和"用户确认"两次执行，没有检查点就
无法在确认后从原位置继续。

**Q：为什么不用 LangChain 的向量库和 `ToolNode`？**
A：M1 阶段要的是"可解释、可控"。检索用原生 SQLite FTS5（后面在 M2 加向量 +
RRF，仍是自己的检索层），权限用自定义 `tools` 节点。框架负责编排，**决策留在
自己手里**——这样每一层都能单独测试、单独解释。

## 十三、学习闭环（M3）

把"错题 → 出题 → 练习 → 掌握度 → 规划"串成一个闭环，数据在 `learning.py`。

- **错题（feedback）**：带学科标签；学科来自"记录时选中的知识库"。
- **出题（generator.py）**：从知识库片段或错题生成题目。**模型写题，失败回退模板**
  （无模型 / Mock / 解析失败都回退）——出题永不因模型问题而失败。
- **一条误区只出一题**：`(user_id, source_feedback_id)` 上的**部分唯一索引**保证。
- **间隔重复**：每题有 `due_at`；作答自评 again / hard / good / easy → 掌握度增减 +
  下次复习间隔（again 立即、good 3 天、easy 7 天）。这是可解释的固定间隔，未来
  可替换为 SM-2 之类的算法而不动数据边界。
- **掌握度**：按学科维护 0~100。
- **长期记忆（memory.py）**：规则抽取"记住：… / 我的目标是… / 我在准备…"等**明确**
  句式（抽错比抽不到更糟）；注入提示词时标注"仅作背景，不是指令"。
- **今日复习（planner）**：汇总到期题 + 薄弱学科 + 近期误区，给出建议列表。

对应的 HTTP 接口见 §九。图状态用 `memories` 字段承载注入的长期记忆（`state.py`），
`build_system_prompt` 把它拼进系统提示词——**图本身不碰数据库**，记忆由应用层
（`interfaces/api.py` / `interfaces/cli.py`）加载后放进状态，保持图与存储解耦。

## 十四、评测与回合诊断（M5）

**评测（离线考卷）**：把"改动了 prompt/检索/工具之后，系统变好还是变坏"变成可复现的数字。

- `domain/evaluation.py`：纯指标 `hit_at_k` / `reciprocal_rank` / `mean`。
- `application/evaluation.py`：检索评测（灌固定语料 → 固定问题 → Hit@K/MRR）、
  意图评测（固定标注句 → 准确率）、以及**基线对比**（掉超过容差即回归）。
- `interfaces/evals.py`：命令 `zhiji-eval retrieval|intent --dataset ... --baseline ...`，
  有回归时退出码 1，可直接进 CI。检索评测**强制 Mock 向量**，保证同版本同分数。
- 数据集与基线在仓库根的 `evals/`（不在分层包里——它是数据，不是层）。

**回合 trace（诊断）**：把一段会话历史读成"哪一步出了问题"。

- `application/trace.py` 的 `diagnose()` 是纯函数：接收消息历史 + 状态，输出
  `attribution`（`retrieval` / `tool` / `model` / `ok`）与 `warnings`。
- `interfaces/trace.py`：命令 `zhiji-trace --thread <id>`，从检查点取历史并打印
  诊断树。归因逻辑很直接：**检索返回空结果 → retrieval；工具失败 → tool；
  没有最终回答 → model；否则 ok**。

> 为什么归因层只有四类：更细的"编排层 / 费用层"需要每回合的**事件元数据**
> （如预算回退标记、回合超时原因），当前只从消息历史推断，属于已知边界（见下节）。

## 十五、护栏、工具可靠性与上下文工程（M6）

依据业界共识（OpenAI《A practical guide to building agents》把 **guardrails** 列为核心组件、
Anthropic《Effective context engineering》讲 **上下文压缩**），补齐三个模块：

- **护栏（Guardrails）**：`domain/guardrails.py` 是纯规则——输入查空/超长/**提示词注入**，
  输出查空回答/**系统提示词泄漏**/**执行细节泄漏**；`application/guardrails.py` 组装拒绝
  话术。接口层在进图前 `screen_input`、拿到回答后 `screen_output`（API 以 `event: guard`
  告知）。
- **「技术过程内隐」在执行层的兜底**：教学总纲要求正文不讲执行，但**提示词是劝告、执行层
  才是闸门**——`check_output` 会扫一组**内部工具标识符**（内置九件套 `calculator` /
  `knowledge_search` / `mistake_search` / `save_note` / `web_search` / `fetch_url` /
  `write_file` / `read_file` / `list_files`，外加 `mcp_` 前缀兜住运行时才注册的 MCP
  外部工具；大小写不敏感）。这类串在教学回复里**永远不会合法出现**，命中即判"疑似泄漏
  执行细节"、触发 `guard` 事件复核。内置九件套与 `application/tools.TOOLS` 的一致性由
  `test_tool_leak_markers_cover_registry` 守住（新增工具漏挂会被测出来）。
  只拦**标识符**、不拦口语词：正文出现「计算器」「检索」不算违规。
- **工具可靠性**：`application/tool_runner.py` 给每次工具调用加**单次超时**与**有限退避重试**；
  **只对可重试错误重试**（超时、网络类），参数错误立即失败。工具最终失败会转成
  `[tool_error]` 工具消息返回给模型，**不让整回合崩掉**。
  （注意：HITL 的 `GraphInterrupt` 必须原样上抛，不能被当成工具错误吞掉。）
- **上下文压缩**：`application/context.py` 在历史过长时保留最近轮次、把更早的压成一句提示；
  **裁剪只从整轮边界（HumanMessage）开始**，避免把"工具调用/工具结果"拆散。

## 十六、规划、模型路由与成本（M7）

- **规划（Plan-and-Execute）**：`domain/planning.py` 判断"是否需要规划"（复杂请求 =
  超长或含"一步步/先/然后"等），`application/planner.py` 让模型出计划、失败回退规则计划；
  图里新增 `plan` 节点，复杂请求先规划再执行、简单请求跳过（省延迟与成本）。
- **模型路由**：`domain/model_routing.py` 按意图与长度给请求分档（small / standard / large）；
  `build_graph` 接收一个 `model_router(tier, effort)`，接口层按档位返回不同模型（未配置则复用同一个）。
- **轮级推理力度（M12）**：`model_routing.reasoning_effort()` 按意图给出 reasoning_effort
  （讲解/出题 = max，计算/闲聊 = low，中间档 None 交模型自动判断）——参考 GLM
  reasoning_effort 的分级设计。`ZHIJI_REASONING_EFFORT=auto` 开启；基础设施层按
  provider 白名单（DeepSeek/GLM）决定是否附加，普通模型不认该参数就不发。
- **上下文缓存利用（M12）**：系统提示词结构**稳定前缀在前、动态内容在后**
  （人格/规范逐字节一致 → 命中上游隐式缓存，命中 token 半价）；token 记账增加
  `cached_tokens`（来自 `usage_metadata.input_token_details.cache_read`），
  用量卡片可见"缓存命中 N"——缓存省了多少钱有账可查。
- **结构化输出 JSON 模式（M12）**：出题 / 规划 / 智能选库三处统一走
  `application/json_mode.py` 的 `invoke_json()`——优先带
  `response_format=json_object` 请求（服务端保证合法 JSON），provider 不支持
  自动回落普通调用；解析失败率大幅下降，原有容错解析保留作兜底。
- **成本控制**：`infrastructure/usage_repository.py` 记录每次模型调用的 token
  （来自 `usage_metadata`）；`agent` 节点写入用量、并在调用前查**当日预算**，超限即
  `block`（返回提示、不发起真实调用）。`GET /api/usage` 可查当日用量与按模型汇总。

> **一个踩过的坑**：从节点里同步写 SQLite 会**阻塞事件循环**，导致同一文件上的
> 检查点连接无法释放锁（`database is locked`）。修法是把写库放到 `asyncio.to_thread`，
> 并给所有连接开 **WAL + busy_timeout**。

## 十七、MCP 外部工具（M8）

Anthropic 把 **MCP（Model Context Protocol）** 作为连接外部工具/能力的标准方式。
这里自写了最小 **stdio JSON-RPC 2.0 客户端**（`infrastructure/mcp_client.py`，零依赖）：

```text
启动 server 子进程 → initialize 握手 → tools/list 发现工具 → tools/call 调用
消息：换行分隔的 JSON（stdio 传输约定）
```

`infrastructure/mcp_bridge.py` 把发现的外部工具**动态注册进工具表**：
- 从 `inputSchema`（JSON Schema）生成参数模型；
- 名称加 `mcp_<server>_<tool>` 前缀，避免与内置工具冲突；
- **server 起不来或列工具失败不阻塞应用启动**（MCP 是可选增强）。

配置即接入：`ZHIJI_MCP_SERVERS='[{"name":"fs","command":"npx","args":["-y","@modelcontextprotocol/server-filesystem","/tmp"]}]'`。
MCP 工具是**默认关闭、按需授权**的：`AgentProfile.mcp_enabled` 默认 `False`，
只有 `tutor` / `retriever` 显式开启——schema 层不并入默认集，执行层
`is_tool_allowed` 还会再拦一次（`is_mcp_tool` 判定）。`deny_all` 的进度 agent
、只读的练习 agent 和计算 agent 都拿不到任何外部工具。

## 十八、会话系统、附件与知识库阅读（M9）

这一节记录"把 Demo 变成能天天用"的一轮改造：会话管理、附件、过程流、知识库阅读。

**1. 项目空间与记忆隔离**

- 表：`projects`（含 `is_default`）、`chat_sessions`（带 `thread_id`）、
  `chat_messages`（`attachments` / `steps` 两个 JSON 列）；记忆表 `memories` 增加 `project_id`。
- 首次访问 `/api/projects` 会**幂等创建系统兜底空间「未归类」**，并把历史无主会话收编进去。
  它**不是**给新对话用的默认空间：新对话在前端强制显式选课程（没有课程时引导一键创建
  常用课程），后端保留这个隐藏空间只为兜住旧数据与直连 API 的请求。
- **记忆按项目隔离**：`list_memories(project_id=...)` + 提示词只注入本项目记忆。
  不带 `project_id` 的请求会兜底到默认空间——否则记忆会落进 `project_id=''` 的黑洞桶，
  表现就是"明明让它记住，它却忘了"（这是真实踩过的坑）。
- **刻意不做**跨项目移动会话：会话归属是语义约束，移动会让上下文与记忆错配。

**2. 附件（三条上传路 + 落盘预览）**

- 前端三条路共用一套上传函数：＋菜单选择、**Cmd+V 粘贴**、**拖入输入框**。
- 后端 `POST /api/chat/attachments`：PDF/TXT/MD 抽文本；**图片走视觉转写**
  （`application/image_notes.py` → 规范 Markdown）。图片原文件落盘 `data/attachments/`，
  `GET /api/chat/attachments/{id}/raw` 带归属校验提供预览。
- 一条消息最多 6 个附件，单附件**取前 8000 字**拼进消息——防止长文档撑爆上下文。
- 附件表记录 `project_id`：消息发出前会话可能还不存在，删项目时才能一并清掉孤儿附件。

**3. 过程流（step 事件）**

`_steps_from_update()` 把图节点更新翻译成过程步骤：`route` → 意图中文名 + 子智能体、
`plan` → 编号计划、`agent` → 工具调用 + 参数摘要、`tools` → 结果摘要（失败标记）。
前端渲染成"知迹 智能体 · 已处理 42s"卡片 + 可折叠步骤列表，**步骤随消息落库**
（`chat_messages.steps`），历史回放同样能看到当时的思考过程。

**4. 知识库阅读（Obsidian 式）**

笔记页三栏：常驻共享文件树（`KnowledgeTree`，跨页事件同步）+ 正文 + 右侧双 tab
面板（AI 助手 / 目录大纲）。面板**内联折叠展开**（点当前 tab 收起成 44px 图标条），
拖拽调宽；大纲带缩进线、折叠、scroll-spy 高亮。

> 交互教训：曾把右栏做成"窄屏浮层抽屉 + 黑色遮罩"，用户反馈"正文变黑了"——
> 阅读型页面不要用遮罩抢层，**内联推挤**比浮层更符合心智。

## 十九、日程（时间轴 + 收件箱）

**一句话模型**：`schedule_tasks.date` 为空 = 留在收件箱；非空 = 排进那天的时间轴
（`start_minutes` 是当天分钟数）。

**为什么排期不用模型**：「安排到今天」的结果必须可预期、可复现、零成本——
用一条确定性规则比让模型猜好得多：

```text
时间轴可视范围固定 06:00–24:00
从当天已有任务里找第一个「放得下 duration」的空档
今天则从当前时刻（向上取整到 5 分钟）之后开始找
找不到完整空档 → 接在最后一个任务之后；超出 24:00 → 贴到末尾（允许视觉重叠）
```

这段逻辑在 `application/schedule_service.py` 的 `_first_free_slot()`，测试里用
"两库同命中"式的确定性断言锁死了行为（`tests/test_schedule.py`）。

**数据与接口**：`GET /api/schedule`（日视图 + 收件箱计数）、`/api/schedule/inbox`、
`/api/schedule/week`（周日开头 7 天密度，供周条圆点）、`POST|PUT|DELETE /api/schedule/tasks`、
`POST .../arrange`（一键安排）、`POST .../unarrange`（退回收件箱，保留时长）。

**前端交互要点**：

- 时间轴固定刻度（18 小时 × 44px），打开页面自动滚到当前时刻；现在时刻是虚线 + 时间胶囊。
- 任务卡按时长成比例；**状态靠底色与起点圆点区分**（进行中浅青 / 待办白 + 阴影 / 已完成降饱和划掉）。
- 空白时段悬停出现「＋ 在这里加一件事」，点击即以该时刻新建。
- 自绘时间/日期选择器（`components/SchedulePickers.tsx`）：弃用系统原生控件，
  时分双列（5 分钟一档）+「现在」+ 常用时段；日期是迷你日历（周日开头、翻月、回到今天）。

**已知边界**：只做单日视图（无跨天拖拽、无重复任务、无提醒推送）。
